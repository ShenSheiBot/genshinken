# 西方負典 · 译前处理原则

规定**译前处理（文本清洗）阶段**的约束——原始稿件 / 译文在**进入** `source/_posts/*.md` **之前**应完成的规范化。
处在「来源 → 译前处理 → 翻译 → 落库 md → 博客」链条中的清洗这一环。落库后的写作规范见
[`delivery-standards.md`](delivery-standards.md)。**所有记号一律 ASCII，不夹中文。**

---

## 0. 最高优先级：保真，不得重写

“文本清洗”默认只指**机械保真清洗**，不包含编辑、润色、摘要或重写。原文的字词、自然段、顺序、论证、语气、修辞、重复、犹疑和节奏均属于受保护内容；所谓“更通顺”“更像文章”不构成修改授权。

### 0.1 绝对禁止

未经用户明确要求另作改写稿，不得：

- 删除、合并、拆分或重排自然段；
- 概述、缩写、扩写、释义或同义改写；
- 补写过渡、背景、结论或“更清楚”的论证；
- 把口语、讽刺、激烈措辞、重复、犹疑和机器翻译感改成中性论文体；
- 以“病句”“不流畅”“信息重复”为由重写整句；
- 使用 AI 生成全文覆盖 Outline 原文、仓库原稿或已登记源文快照。

真正的摘要、润色、重组或改写必须另立文件／文档／slug，明确标为“改写稿／摘要稿”并注明来源，不得覆盖、改名顶替或静默删除原稿。

### 0.2 允许的机械清洗不是自由改写权

允许处理的类别仅限：

- 统一 CRLF/LF、文件末尾换行及不承载内容的边界空白；不得改动正文内部有意义的空格；
- 文件名、slug、脚注、链接、图片路径和 Markdown 记号规范化；
- 成对直引号转方向性弯引号；
- 有页图、录音或可信底本逐项支持的 OCR 错字修正；
- 用户明确逐项指定的字词修订。

上述类别只是政策白名单，不代表模型可以自行解释和执行。自动机械转换必须在 `preservation-manifest.json` 中声明，并由确定性脚本实现；脚本尚未实现的转换不得临时由模型自由发挥。

### 0.3 文本保留率与差异门禁

本项目不采用“95% 相似”“大意未变”或模型语义判断等模糊阈值。门禁标准是：

- 统一换行、BOM 和文件末尾换行后，扣除清单中声明的确定性机械转换与逐项授权修订，**正文字符保留率必须为 100%**；
- 自然段的数量、边界和顺序必须 **100% 一致**；
- 未授权的新增、删除、替换、合并、拆分和重排数量必须为 **0**；
- 任何一个字符或段落不符合预期，`npm run verify:preservation` 必须失败，不得用相似度、人工目测或“仅是润色”放行。

### 0.4 哪些修改必须逐项可追踪

- 自动机械转换：在清单中记录转换名称、源文件 SHA-256、来源 URL、拼接顺序，并由版本化脚本确定性执行。
- OCR 订正和用户指定字词修订：每一项都必须在对应文档的 `authorizedChanges` 中登记稳定 id、类型、精确 `find`／`replacement`、理由、证据、授权人和授权日期。
- 每项授权修订的 `find` 必须在应用时唯一匹配，且不得跨越换行；缺失、歧义或试图改变段落结构时直接失败。
- front matter、来源登记和公开 URL 的变更通过 Git diff 追踪；不得借修改元数据之名替换正文。

### 0.5 强制工作流

1. **先快照**：修改前读取并保存完整源文、来源 URL；Outline 文档还须保存文档 ID、修订号和完整正文，不得只保存节选或搜索结果。
2. **再登记**：需要派生博客正文的源文放入 `editorial-sources/`，并在 `editorial-sources/preservation-manifest.json` 登记 SHA-256、来源、拼接方式、允许转换和授权修订。
3. **追加式历史**：运行 `npm run verify:snapshot-history`；既有快照不得修改、删除或改名，只能新增版本文件。
4. **确定性生成**：运行 `npm run sync:preserved`；脚本必须先验证全部清单、路径和源哈希，再写入任何派生正文。
5. **严格校验**：运行 `npm run verify:preservation`；字符、段落或顺序不一致即失败。
6. **失败即停止**：校验失败时禁止更新其余文档、提交、推送或部署，并立即从源文／Outline 历史恢复。
7. **回读**：Outline 更新后必须重新读取全文，与预期正文做严格比较；仅“更新成功”不构成验收。

临时比较两个文件：

```bash
node scripts/verify-source-preservation.mjs --before path/to/before.md --after path/to/after.md
```

若唯一允许差异是成对 ASCII 双引号转弯引号，可追加 `--smart-double-quotes`。

已登记源文快照不可原地修改；合法订正必须新增带版本标识的源文件，并经用户明确授权后更新清单。

## 1. 文件与 URL：ASCII 化

slug / 文件名规范化为 ASCII（小写、数字、短横线）。细则见 `delivery-standards.md` §1。

## 2. 引号规范化

正文 ASCII 直引号 `" '` 转为方向性 Unicode 弯引号（`“ ”` 双 / `‘ ’` 单）。front-matter 值、图片 `title`
不经前端构建期规范化，须在此阶段改正。

## 3. 脚注统一为 GFM

一切脚注（Word/Outline 导出的 `_ftnref` 锚点、纯文本角标等）统一改写为 GFM：正文 `[^n]` + 文末 `[^n]: 定义`。
不要手写 `## 注释` 标题或脚注前的 `---`；文末「注释」区由前端自动生成。

## 4. 承接段标记

自然段中插入引文后承接该段的段落，于该段**前一行单独**写哨兵记号 `<!--continue-->`：

```markdown
> ……引文最后一行。

<!--continue-->

在英国的清算联盟方案……（承接段，前端将不缩进首行）
```

记号必须**独立成行**（与正文同行会被 CommonMark 当作 HTML 块吞掉整段）。渲染管线（`lib/markdown.ts`）
识别紧邻其下的段落、抹掉记号并赋 `.cont`（首行不缩进）。其余段落默认首行缩进两格。

## 5. 内链与图片

- Outline 内部 `mention://` 链接在公网无意义，替换为真实 URL 或纯文本。
- 图片落到 `public/attachments/`，正文用相对路径 `attachments/...`。

## 6. front-matter 补全

落库前补全 YAML：`title` / `date` / `slug`(ASCII) / `categories` / `tags` / 署名等。细则见
`delivery-standards.md` §2。
